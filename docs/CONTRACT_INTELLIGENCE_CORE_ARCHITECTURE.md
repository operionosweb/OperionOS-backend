# Contract Intelligence Core Architecture

## Scope

This milestone extends the existing production contract pipeline. It does not add a second workspace, AI stack, document store, or aviation UI. Deterministic demo data remains an explicitly labelled fallback.

## Discovered architecture

- **Runtime:** Express 5 in `index.js`, with route modules under `routes/`.
- **Authentication and tenancy:** Supabase user authentication, organization membership, role permissions, organization predicates in repositories/services, and PostgreSQL RLS.
- **Database:** Supabase PostgreSQL migrations under `supabase/migrations/`. The production entities already include organizations, contracts, documents, versions, extractions, analysis runs, parties, clauses, obligations, deadlines, risks, recommendations, evidence, search chunks, aircraft, and aircraft-contract relationships.
- **Storage:** private Supabase Storage bucket `contract-documents`; immutable tenant-shaped object keys; source paths are removed from API responses.
- **Upload:** `POST /api/contracts/upload` accepts memory-buffered PDF/DOCX files, validates bytes/MIME/size, stores the original, and creates tenant-scoped contract, document, version, extraction, structure, and analysis-run records.
- **Text/structure:** `documentIngestionService` uses `pdf-parse` and `mammoth`; `documentStructureService` persists pages, sections, and chunks.
- **Intelligence stages:** Phase 3 services provide deterministic clauses, obligations, deadlines, risks, evidence, and optional existing AI-gateway normalization/reasoning.
- **AI:** the existing `aiGateway` and `contractAssistantService` are the only provider and grounded-answer paths to extend.
- **Search:** PostgreSQL search chunks and existing search services provide the foundation; results must remain tenant-scoped and evidence-addressable.
- **Aviation:** migration 015 already models global aircraft plus tenant-scoped many-to-many `aircraft_contract_relationships`.
- **Frontend:** the protected production `ContractWorkspace` already resolves contract -> document -> version -> analysis run -> intelligence APIs. The demo workspace and synthetic Live Tracking provider remain fallback surfaces.

## Implemented flow

Upload persists PDF page boundaries where available and ordered DOCX structure without fabricated page numbers, and creates a queued analysis run. `POST /api/analysis-runs/:id/process` composes deterministic clauses, obligations, deadlines, risks, profile generation, full-text indexing, and exact tenant-aircraft relationship matching behind explicit analysis state transitions. The production Contract Workspace invokes this operation, polls status, and displays the profile and search results. Manual stage endpoints remain available for compatibility. Previously persisted DOCX results may still contain inaccurate page numbers and require separate review.

Migration `016_contract_intelligence_core.sql` and its clean-database/live validation coverage are implemented in the repository. It must be applied to the target Supabase environment before the profile, relationship-evidence, and contract metadata writes can run there.

## Implementation plan

1. Preserve actual PDF page boundaries and ordered DOCX blocks in the existing extraction representation.
2. Extend the current schema for supported contract metadata, classification confidence, summaries/claims, processing errors, and relationship evidence without duplicating Phase 3 tables.
3. Add deterministic aviation-first metadata/classification, summary, recommendation, and aircraft-identifier extraction services. Unknown values remain null.
4. Add one idempotent pipeline orchestrator over the existing clause, obligation, deadline, risk, evidence, search, and relationship repositories. Persist state transitions and terminal failures.
5. Expose orchestration, summary, search, evidence, and relationship capabilities through the existing contract/analysis/aviation route conventions with current auth and tenancy middleware.
6. Connect the existing production Contract Workspace and current Live Tracking dependency experience to these APIs, retaining explicit demo fallback.
7. Validate with a clearly synthetic aircraft-lease fixture. Core extraction tests remain deterministic; provider behavior is mocked where AI is exercised.

## Processing semantics

- Document ingestion states: `uploaded -> processing -> ready|requires_ocr|failed`.
- Analysis states: `queued -> processing -> extracting -> analysing -> indexing -> completed|failed`.
- `ready` means source text and structure are stored. It does not mean contract intelligence is complete.
- Reprocessing the same document version and pipeline version must reuse or replace the same scoped stage outputs rather than duplicate them.
- Persisted gateway job errors use an allowlisted code and a generic message; other error and logging paths still require a complete sensitive-data review.
- Newly persisted provider-normalized obligations require human review regardless of provider-supplied status. Optional deadline fallback requires a source-clause timing quote, rejects unsupported numeric amounts, units and recurrence, and marks new results for review. These checks do not prove an interpretation is correct and do not rewrite previously persisted records. Existing numeric confidence values are not calibrated probabilities.

## Provider decision and release boundary

The process endpoint remains deterministic by default. An optional Azure AI review is prepared but disabled unless an operator explicitly attests to all required approvals and a user confirms document authorization and budget usage. No provider account or customer-data processing arrangement has been approved or verified for Operion. Provider mocks exercise code paths only; they do not establish model accuracy, data protection, or an end-to-end AI workflow.

**Conditional candidate:** evaluate a regional Azure OpenAI deployment in Microsoft Foundry, with a specific model supporting [JSON Schema structured outputs](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/structured-outputs). Microsoft states that prompts and outputs are not used to train foundation models without permission, and standard deployments process them within the customer-specified geography. Global and DataZone deployments have different processing-location rules; stateful features and abuse monitoring can retain content, and modified monitoring requires approval ([Microsoft privacy documentation](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy)). [Pricing](https://azure.microsoft.com/en-us/pricing/details/azure-openai/) depends on model, region, deployment and usage and must be quoted for the intended configuration.

OpenAI states that API data is not used for training by default, but abuse-monitoring logs can retain content for up to 30 days by default; zero-data-retention controls require eligibility and approval and have endpoint limitations ([OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)). Mistral's published [DPA section 2.3](https://legal.mistral.ai/terms/data-processing-addendum/?language=en-US) permits training unless opted out, and describes separate feedback-related training; the applicable business agreement and account settings require verification. These descriptions do not establish the terms of Operion's account.

Before any customer contract is sent to a provider, the owner must approve the provider and applicable DPA, no-training terms, subprocessors, processing geography, abuse-monitoring and retention settings, deletion process, model, cost and legal basis. Independently verify an isolated database and private storage, tenant RLS, secrets management, test-data deletion and source-grounding. Use synthetic documents until these conditions and document-owner authorization are established. No provider is selected for production by this recommendation.

The prepared integration reads server-only `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_DEPLOYMENT` and `AZURE_OPENAI_API_KEY`. The four server-side attestations `CONTRACT_AI_ENABLED`, `CONTRACT_AI_PROVIDER_APPROVED`, `CONTRACT_AI_ISOLATION_VERIFIED` and `CONTRACT_AI_DATA_USE_APPROVED` must each be `true`; these flags are operator assertions, not proof of approval or isolation. An authenticated organization user with analysis permission must separately request AI and confirm document authorization and budget use. Do not set these flags until the approvals and infrastructure checks above are complete. No credentials belong in the frontend.

AI findings are stored separately in profile metadata, with exact evidence quotes and mandatory human review; model confidence is uncalibrated. A quote match does not establish semantic correctness or completeness. The integration rejects truncated input, input above 100,000 characters, invalid structured output, missing source quotes and unsupported numeric values rather than presenting a partial success. Azure response caching is disabled for this operation. A queued analysis is claimed with an atomic tenant-scoped status update; unfinished or failed runs require manual review rather than automatic replay, including when an AI profile was persisted. Inspect provider usage and the retained run before explicitly creating a new run. Completed deterministic profiles are immutable and require a new analysis run for AI review.

Azure requests allow one completion with at most 4,096 generated tokens, including reasoning tokens, and time out after 60 seconds. A length-truncated completion is rejected. Input is bounded by characters and HTTP body size, not by a model-specific tokenizer; a verified input-token limit and pricing estimate remain prerequisites for controlled live execution. Verify that the approved deployment supports the completion limit and structured output before activation.

`npm run validate:contract-ai:preflight` reports missing local configuration and approval attestations without printing values or contacting remote systems; it does not verify isolation or execute a live contract. `npm run validate:contract-ai:live` requires those attestations and `CONTRACT_TEST_DEPLOYMENT_LIMITS_VERIFIED=true`, uses dedicated pre-existing test tenants, and retains created test data. It requires an operator to verify the deployment's actual token limits and account arrangements; its 12,000-byte source bound is not a model-specific token count. After any failed or uncertain run, inspect retained test records and provider usage before retrying. Neither command establishes production readiness.

Uploads and analysis runs use transaction-scoped PostgreSQL advisory locks to reject concurrent equivalent operations. Document and version records are reserved before object upload, and incomplete uploads require review rather than automatic deletion or retry. After an observed lock-connection error, the upload and analysis orchestrators stop at their next stage boundary and do not attempt failure-status writes. Operations already in flight cannot be cancelled by this check, and a lock can be lost before the client observes the disconnect. This is not a lease or database-enforced fencing. The analysis retry service rejects failed-run retries pending manual review instead of creating an unusable `processing` run.

Migration `031_contract_upload_journal.sql` adds a service-role-only reservation RPC that creates a contract when needed, document version and journal atomically, and records scoped state transitions in an append-only event table. Ingestion verifies downloaded object bytes against their original size and SHA-256 before marking storage verified. Incomplete or uncertain operations remain for manual review; the journal is not an automatic recovery engine.

Migration `032_contract_analysis_dispatch.sql` stages a run as `awaiting_ingestion` while its source and structure are persisted. The journal's transition to `ready` atomically verifies the persisted extraction and structure and inserts a unique analysis outbox event. A service-role-only dispatch RPC atomically changes the event to `dispatched` and queues the run; repeated dispatch returns the same run. A bounded batch RPC can dispatch pending events with `SKIP LOCKED`, but no background scheduler is installed. It queues analysis only: it never invokes AI. OCR-required uploads remain staged and are not dispatched. If a terminal journal acknowledgement or dispatch response is uncertain, ingestion preserves the records instead of marking them failed; inspect the journal and outbox before retrying.

The service-role-only `inspect_contract_upload_recovery` RPC provides a bounded, tenant-scoped dry-run classification of journal and dispatch states. It identifies pending dispatch as retry eligible and conservatively classifies uncertain or OCR states for manual review. It does not inspect Storage or establish whether an upload is still active. The separate bounded dispatch RPC can recover pending dispatches; it does not recover document transfers or analysis execution.

These locks require database connectivity and remain held across external operations; a lost connection or database idle-transaction timeout can release a lock before those operations finish. Storage and PostgreSQL are not one transaction. Extraction, structure and status writes can still be partial. The batch dispatcher has no automatic scheduler, attempt history or poison-event handling. There is no general reconciliation engine, durable worker lease or database-enforced stale-worker fencing; readiness checks do not fence stale workers. No uncertain AI operation may be automatically replayed. A checksum-scoped reservation is not a complete client idempotency protocol. Migrations 031 and 032 and their integration are local work in progress, not authorization to apply them to any hosted database. Do not treat this implementation as sufficient for production or a paid pilot.

### Local analysis-worker fencing (not deployed)

Migrations `033_analysis_fence_foundation.sql`, `034_analysis_execution_guard.sql`, and `035_analysis_worker_fencing.sql` establish the local fencing path. Migration 035 removes the fence-row activation block and adds a service-role-only, one-time database claim for a queued run whose ingestion and outbox are ready. The claim atomically moves the run to processing and issues a generation-1 worker/execution identity and token. There is no transfer, heartbeat, renewal, release, reclaim, or automated recovery; the claim expires after 24 hours and an expired run can remain blocked pending manual review. Application code does not receive or log the raw token outside process memory.

The main `contractIntelligencePipeline` now obtains that claim and carries its context into status updates, clause, obligation, deadline, risk, profile, party, relationship and search writes. Fenced PostgreSQL repositories start a transaction, set the context locally, and validate it before writing. Database triggers independently check tenant/run/worker/execution/generation/token/expiry and hold the fence row lock through transaction end. They cover run state, result rows and evidence links. Links require parent and evidence to resolve to the same run whenever either side is managed or active. Manual stage routes and the alternate clause-analysis path do not claim ownership; writes that require a fence fail closed.

Shared contract metadata and aircraft relationship triggers permit a matching active owner context, reject stale or mismatched context, and reject unfenced writes while a related run is active. AI full-contract jobs and usage rows are attributed to the run, with unique run/operation and job accounting constraints. Usage completion is intentionally not result-fenced: an AI provider may already have charged for a response when result ownership expires, so accounting must remain recordable. This prevents duplicate completed usage accounting, but is not a guarantee of provider billing reconciliation or end-to-end exactly-once execution.

This is local implementation, not authorization to apply migrations to a hosted environment. Before any future rollout, a read-only review must determine whether active/queued runs would be blocked by the new guards, check existing duplicate AI usage rows before the unique index, verify provider and database role grants, and establish an approved recovery plan. Do not run these migrations in production. The pipeline stages still commit independently; partial result persistence remains possible if a later stage fails. Migration ownership, database-owner bypass, human edits during active analysis, and complete adapter coverage require additional security and operational review.

The [analysis write inventory](ANALYSIS_WRITE_INVENTORY.md) records each identified path and evidence status. The disposable rehearsal exercises the database claim, real deterministic clause service/repository, shared-write guards, fenced status and rejection/rollback cases, but does not execute the entire pipeline across every production adapter. No hosted RLS, Supabase Storage, or production role behavior has been verified.

The clean-room schema inventory covers migrations 001-035. `test/phase88-postgres-rehearsal.js` runs the canonical schema and populated 032-to-035 upgrade, reservation, dispatch and fence tests using a disposable Windows PostgreSQL installation: set `PHASE88_PG_BIN` to its binary directory, `PHASE88_PG_TMPDIR` to a task-owned temporary parent and `PHASE88_DISPOSABLE_DATABASE=yes`, then run `node test/phase88-postgres-rehearsal.js`. It creates a new loopback-only cluster and removes only its own temporary directory after shutdown. Its Auth and Storage schemas are stubs, not Supabase services; this rehearsal does not verify actual object storage, production data or hosted RLS.

The separate `npm run test:supabase:local -- <local-status-file>` harness requires an isolated local Supabase stack and a private status file containing its local-only credentials. It currently expects only migrations 001-021 and deletes its own synthetic resources. Do not run it against shared or hosted infrastructure; update and review its migration and cleanup behavior before using it for the current chain.

The Demo browser test no longer prints captured page-error text or page bodies on heading failures. This limits one diagnostic exposure path; it does not identify or resolve the earlier Knock token-like fragments, and other logging paths still require review. The integration owner must assess whether the earlier fragments were valid credentials and whether revocation or rotation is warranted.

Gateway intelligence units are estimates, not monetary charges. Provider failures, refusals, malformed JSON or timeouts can still incur provider charges even if the gateway releases its reservation; reconcile actual billing before enabling the integration.

## Evidence invariant

Every persisted finding or recommendation that asserts contract content must carry or resolve to the same tenant-scoped document version, page, clause/section, character/block locator, and exact source excerpt. Relative deadlines remain relative unless a supported trigger date establishes a calculation basis. Aircraft relationships require an identifier found in source evidence or an explicitly labelled demo fixture.
